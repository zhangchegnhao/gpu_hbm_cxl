# Qwen3 real-pilot runtime-v1 analysis

## 1. Objective and scope

This stage tests whether the exact `sieve-cycle-v1` search can be replaced by a
small online timing model. The exact policy is retained as an offline Oracle;
the new `sieve-runtime-v1` policy makes its placement decision without reading
exact placement candidates or running Ramulator during inference.

The replay still models one GPU and eight Local HBM-PIM stacks for the
Qwen3-30B-A3B BF16 model (48 layers, 128 experts, Top-8). The input is the
existing real pilot Router Trace: 384 layer-batches, Batch 8, and eight Decode
steps. The replay backend is `ramulator-contention-v1`, so the final selected
placement is evaluated with the existing exact contention table after the
decision has been made.

This is an in-sample feasibility experiment. It does not establish
generalization to new prompts, batch sizes, context lengths, models, or
hardware.

## 2. Runtime policy

After Router output, active experts are sorted by descending token count (expert
ID breaks ties). The policy evaluates every hot-prefix length from zero through
the active-expert count. For a candidate prefix it predicts:

```text
objective = scheduler_overhead + max(
    predicted_GPU_READ(expert_count) + analytic_GPU_compute,
    predicted_PIM_pipeline(pim_token_count)
)
```

The prediction curves are piecewise linear. They use 15 non-zero calibration
points:

- GPU READ anchors at expert counts `1, 2, 4, 8, 16, 32, 49`;
- PIM pipeline anchors at token counts `1, 2, 4, 8, 16, 32, 48, 64`.

The zero point is fixed at `(0, 0 us)` for each curve. The anchors are extracted
from exact isolated timings already present in the cycle-v1 table. In a future
hardware deployment these points should be collected as a small independent
microbenchmark. The exact contention table is not consulted by the runtime
policy; it is used only for post-decision simulator ground truth and for the
Oracle comparison in this experiment.

## 3. End-to-end result

| Policy | Total latency (ms) | Relative to runtime |
|---|---:|---:|
| `sieve-cycle-v1` (offline Oracle) | 30.551096 | -0.000064% |
| `sieve-runtime-v1` | 30.551116 | baseline |
| `sieve-fixed-16-cycle-v1` | 34.003663 | +11.300% |
| `sieve` (legacy) | 37.673216 | +23.312% |

The runtime policy is only `0.019553 us` slower than the Oracle over the full
pilot, a `0.000064%` gap. It reduces simulated latency by `18.9049%` relative
to legacy `sieve` and by `10.1535%` relative to the fixed-16 ablation. No new
Ramulator workload was run in this stage.

These are simulator wall-clock totals for the configured 8-request, 8-step
pilot, not hardware measurements. The runtime decision itself uses the
configured 20 us scheduler overhead; this evaluation does not claim that the
offline calibration time is part of an online request's latency.

## 4. Decision agreement and prediction error

The runtime and Oracle policies select the same GPU prefix in 380 of 384
layer-batches (`98.9583%`). The four disagreements differ by one GPU expert.
The selected runtime prediction never extrapolates beyond the calibrated ranges
in this pilot. The exact per-layer comparison is in
`results/full_decode_real_pilot_runtime_v1/runtime_evaluation/layers.csv`.

For non-anchor count values observed in this same pilot:

| Predicted path | Holdout counts | MAE (us) | Max error (us) | MAPE |
|---|---:|---:|---:|---:|
| GPU READ | 42 | 0.019528 | 0.034944 | 0.04525% |
| PIM pipeline | 54 | 0.010227 | 0.018408 | 0.03746% |

The decision regret is `0.00005092 us` on average, `0 us` at the P95, and
`0.00488832 us` at the maximum (`0.009334%` of the corresponding Oracle layer
objective). The regret is measured against exact post-decision contention
timing and therefore does not make the runtime predictor itself exact.

## 5. Reproducibility and integrity

The four replay policies (`sieve-runtime-v1`, `sieve-cycle-v1`,
`sieve-fixed-16-cycle-v1`, and legacy `sieve`) each contain 384 layer records,
384 contention records, complete event/step/placement files, and a run manifest.
The evaluation script rejects a result if its policy name, timing backend,
layer-batch count, or input hashes do not match the current experiment.

The runtime calibration loader validates its schema, sorted monotonic anchors,
finite non-negative durations, and SHA-256 provenance. The calibration and
replay bind to the current model, hardware, cycle configuration, real Router
Trace, manifest, and exact contention table. The generated calibration and
evaluation files are:

- `ramulator/timing_tables/generated/qwen3_real_pilot_runtime_calibration_v1.json`;
- `ramulator/timing_tables/generated/qwen3_real_pilot_runtime_calibration_v1.evidence.json`;
- `results/full_decode_real_pilot_runtime_v1/`;
- `outputs/qwen3_real_pilot_runtime_v1_figures/`.

The figures are generated by
`scripts/plot_runtime_v1_results.py`:

- `runtime_v1_total_latency.png`;
- `runtime_v1_prefix_selection.png`;
- `runtime_v1_prediction_error.png`.

## 6. Interpretation and limits

The result supports a narrower claim: for this fixed Qwen3 real pilot, model,
hardware configuration, and observed count range, a 15-point piecewise-linear
runtime model reproduces the exact Oracle's hot-prefix decisions very closely.
It does not prove cross-workload generalization. New prompts, longer or
continuous decode streams, different Batch/Context combinations, another model,
or another memory system require held-out calibration and validation.

The simulator still uses analytic GPU arithmetic, Router, scheduler, and GPU
Attention timing; PIM Attention is not in the mixed request model; GPU READ is
an abstract ordered request stream rather than a hardware memory trace; refresh,
energy, native per-bank PIM commands, multi-GPU, NVLink, and Shared CXL-PIM are
not modeled. `pimoe` remains a static token-threshold placeholder and is not a
PIMoE paper reproduction. The result must not be described as measured B200
performance or as a complete Sieve reproduction.

## 7. Next experiment

The next scientifically useful test is a held-out workload matrix: reserve
prompts or Router signatures that are not used to select calibration anchors,
then evaluate runtime decisions against exact cycle-v1 timing. Expand Batch,
context length, and decode-step coverage before making a generalization claim.
